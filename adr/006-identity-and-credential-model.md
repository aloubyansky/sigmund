# ADR-006: Identity and Credential Model

## Status

Proposed

## Context

`SignerIdentity` holds a list of `Credential`s, and `TrustVerifier` trusts an
artifact when a credential proven by evidence overlaps with a credential listed
for an expected signer. Three credential types exist today:
`FingerprintCredential`, `EmailCredential` and `SigstoreCredential`.

The attraction of `EmailCredential` was backend independence: one identity that
holds whether the signer uses OpenPGP or Sigstore, surviving key rotation.
`Credential`'s javadoc states this explicitly — an email entry matches both
OpenPGP, via UID parsing, and Sigstore, via the certificate SAN.

Examining how each is proven shows the types are not comparable:

- A **fingerprint** is proven by the signature. Nothing else has to be trusted,
  and it works offline.
- A **Sigstore identity** is proven by a Fulcio certificate: an OIDC provider
  authenticated the subject, and the binding is inside the signed bundle and
  timestamped in Rekor.
- An **OpenPGP UID** is self-certified. The key owner signed their own claim to
  an address. Any key can carry any address.

The last case makes email matching as implemented unsound: a key generated for
the occasion, carrying `alice@example.org` in its UID, satisfies a policy
naming that address — and, because the types are interchangeable, also
satisfies a policy written for a Sigstore identity.

Key material has a gap of its own. `FingerprintCredential.matches` accepts any
value of at least 16 hex characters and matches when either side is a suffix of
the other, so a policy entry holding a 64-bit key ID accepts every key whose
fingerprint ends in those 64 bits. Colliding long key IDs can be generated by a
determined attacker, which is why full fingerprints are the accepted practice.

A second gap has the shape of the UID one. `SigstoreCredential.matches` skips
fields the policy leaves null, the issuer included, so an entry naming only
`source-repository-uri` accepts that repository as asserted by *any* OIDC
issuer Fulcio federates with.

Identity is not optional. Sigmund's premise (ADR-002) is trusting a *signer*,
not a key: a fingerprint covers the keys already seen, and only an identity
lets a policy accept a key the publisher generates next year. Without it every
rotation breaks every policy naming the old key — the rot problem of Gradle's
`verification-metadata.xml`.

A sound binding for an OpenPGP address exists, but it is a property of *where
the key came from*, not of the key: keys.openpgp.org publishes a UID only after
the address owner confirms it by email. `BcRunner.fetchKey` does not record
which source supplied a key, returns early when the local store already holds a
key with UIDs, whichever source put them there, and takes the first keyserver
answer that carries UIDs — so adding a non-verifying keyserver silently turns
unverified UIDs into matches.

Directory bindings are current-state. From the keys.openpgp.org FAQ: an address
is associated with a single key, and verifying it for a new key means it "will
no longer appear in any key for which it was previously verified". That is
exactly right for future keys — the new key is served with the address — and
wrong for history: signatures the old key made lose the binding for a verifier
that never saw it.

## Decision

Two credential kinds. Identities are accepted only from issuers the policy
names — once at the top for entries that do not name one, or inline for a
single entry. A UID is an identity only when a named directory served it;
otherwise it is display text.

### Two credential kinds

```java
public sealed interface Credential permits KeyCredential, IdentityCredential {
    String type();
    String displayName();
    boolean matches(Credential proven);
}

/** Key material, proven by the signature itself. No issuer, no network. */
public record KeyCredential(String type, String fingerprint) implements Credential { }

/** An identity asserted by a third party: the issuer, plus what it attested. */
public record IdentityCredential(
        String issuer,
        Map<String, String> attributes) implements Credential { }
```

`FingerprintCredential` becomes `KeyCredential`. `SigstoreCredential` becomes
an `IdentityCredential` whose issuer is the OIDC issuer from the certificate and
whose attributes are the SAN (`subject`, and `email` when the SAN is an email
address) and the Fulcio certificate extensions. `EmailCredential` becomes an
`IdentityCredential` whose issuer is the directory that served the key and
whose attribute is `email` — one credential per address the directory served,
since a key may carry several verified addresses and an attribute holds one
value. Today only the primary UID's address is extracted.

On the policy side, an identity entry is the same type with the issuer
optional. A separate matcher hierarchy is not introduced until policy needs
something a credential cannot express, such as attribute wildcards.

### Why two kinds rather than three types

The current types are organized by format — an OpenPGP fingerprint, an email
address, a Sigstore certificate. Trust depends on something else: **who vouches
for the fact**. The two kinds are organized by that.

- **Who vouches is part of the type.** A `KeyCredential` is proven by the
  signature and needs no one else; an `IdentityCredential` cannot exist without
  the issuer that asserted it. `EmailCredential` had nowhere to record who
  vouched — in practice nobody did — and making it sound means adding an issuer,
  at which point it is an `IdentityCredential`. Its unsoundness was a limit of
  the type, not a matching bug.
- **Unrelated sources cannot satisfy each other.** One `email:` entry today
  matches both a UID and a certificate SAN, so a self-certified UID satisfies a
  policy written for a Sigstore identity. Requiring a trusted issuer keeps a UID
  from ever becoming an identity, and keeps a directory-verified address
  distinguishable from an OIDC-verified one.
- **Two matching rules instead of three.** Each current class carries its own
  `matches`, and both gaps in the Context come from that: suffix matching in
  `FingerprintCredential`, null-skipping in `SigstoreCredential`. The new model
  has two rules — exact fingerprint; trusted issuer plus attribute subset — each
  stateable in a sentence and auditable.
- **New sources are data, not classes.** `SigstoreCredential` hard-codes seven
  fields, so a new Fulcio extension is a code change. A SLSA builder ID, a VSA's
  `verifier.id`, WKD or an X.509 subject are issuers with attributes; a LibrePGP
  v5 key or an X.509 key is another `KeyCredential` type. The sealed interface
  stays at two permits.
- **The kinds are the threat model's two guarantees** (§1.1). Key policies
  defend against account takeover producing releases under a different key;
  identity policies inherit the issuer's account security. A report can say
  which guarantee an artifact got, which three format-shaped types, with email
  sitting ambiguously between, could not.
- **The kinds differ over time, and policy advice follows directly.** Key
  material is stable, offline and historically complete but pinned to keys
  already seen; an identity survives rotation but may need the network and a
  fresh binding. "Fingerprints for history, identity for keys to come" is one
  credential of each kind on a signer.
- **Backend independence, soundly.** An address verified by keys.openpgp.org
  and one verified by an OIDC provider are the same kind with different issuers,
  so one `email:` entry spans OpenPGP and Sigstore through the issuer list —
  what `EmailCredential` set out to do.

The cost is static typing and bespoke display. A misspelled attribute no longer
fails to compile; the closed per-kind vocabulary below and the published schema
catch it instead, at load and in the editor. Rendering an identity readably — "workflow
`release.yml` in `acme/widget`" — needs formatting per issuer kind rather than
each class's own `displayName()`.

### Trusted issuers

```yaml
issuers:
  - keys.openpgp.org
  - https://token.actions.githubusercontent.com
```

The list is **the default issuer set**: the issuers trusted for every identity
entry that does not name one. Stating it once keeps the common case from
repeating the same issuer on every signer. It is empty by default.

An entry may instead name its own `issuer`, which grants that issuer **for
that entry only**. It does not have to be listed. Requiring it would force a
wider grant than intended: listing an issuer makes it vouch for every
issuer-less entry, so trusting Google's OIDC for one release bot would also let
it vouch for every `email:` in the policy.

Both forms are policy-only and covered by the policy digest. The run report
shows, per signer, the issuers its entries accept, so the effective grant is
reviewable without reading every entry.

There is no per-issuer configuration: an issuer's kind, and so what it can
assert, is known from its name. **Every issuer is canonically an `https://`
URL**, which is what results record. Known directories are checked first, so
`https://keys.openpgp.org` is the directory rather than an OIDC issuer that can
never assert anything; any other `https://` URL is an OIDC issuer. A known
directory may be written without the scheme — `keys.openpgp.org` — as
shorthand; any other name without it is a config error. For a directory the URL
is also its lookup endpoint, so naming one later needs no separate endpoint
setting.

- **OIDC issuers** — any `https://` URL, proven by a Fulcio certificate. They
  assert `subject`, `email` when the SAN is an address, and the Fulcio
  certificate extensions. The trust root that makes the assertion checkable,
  the Sigstore public-good root fetched through TUF by `sigstore-java`, is tool
  configuration, not policy.
- **OpenPGP directories** — issuers that verify addresses before publishing
  them. They assert `email` only. Sigmund knows one, `https://keys.openpgp.org`,
  as a constant in code. A second directory is added the same way, or through
  configuration — a URL with its kind declared — once someone needs one
  Sigmund does not know.

### Attribute vocabulary

What each issuer kind can assert is a closed set, taken from existing
specifications rather than invented:

- **OpenPGP directory:** `email`.
- **OIDC issuer:** `subject`; `email` when the SAN is an address; and the
  Fulcio certificate extensions, named as in Fulcio's OID registry
  (`1.3.6.1.4.1.57264.1.9` onward): `build-signer-uri`, `build-signer-digest`,
  `runner-environment`, `source-repository-uri`, `source-repository-digest`,
  `source-repository-ref`, `source-repository-identifier`,
  `source-repository-owner-uri`, `source-repository-owner-identifier`,
  `build-config-uri`, `build-config-digest`, `build-trigger`,
  `run-invocation-uri`, `source-repository-visibility-at-signing`,
  `deployment-environment`, `token-subject` (`.1.9`–`.1.24`). The deprecated
  GitHub-specific extensions (`.1.2`–`.1.6`) are not adopted.

In code this is one small enum of issuer kinds, each carrying its attribute
set, used by config validation and by the certificate parser that produces
proven credentials.

A misspelled attribute is not a nuisance but a widening: an ignored
`build-config-ur` would leave an entry accepting every workflow in the
repository. So an attribute outside the vocabulary of the entry's issuer kinds
is always a config error, and the message suggests the nearest known name:

```
signer 'release-bot': unknown attribute 'build-config-ur' — did you mean 'build-config-uri'?
```

### Matching

- A `KeyCredential` matches a proven `KeyCredential` of the same type and the
  **same full fingerprint** — 40 hex characters for v4, 64 for v6, compared
  exactly, ignoring case. A key ID or any other shortened value is rejected at
  load rather than matched as a suffix. It never matches an
  `IdentityCredential`. Every OpenPGP backend proves the full fingerprint of
  the key that verified the signature and, when that is a subkey, of its
  primary key, so policy may name either and all backends agree; a signature
  that carries only a 64-bit key ID proves a key only once the verifying key
  is found by it.
- An identity entry matches a proven `IdentityCredential` when the proven
  issuer is the entry's `issuer` if it names one, or otherwise one of the
  listed issuers, and every attribute the entry names is present in the proven
  credential with an equal value. `email` values compare case-insensitively,
  as directories and OIDC providers treat them; other attributes compare
  exactly.
- An entry names at least one attribute besides the issuer; one with only an
  issuer would accept every identity that issuer ever asserts.
- An entry that **none of its issuers can assert** — an issuer-less `email:`
  with no directory and no OIDC issuer listed, or `source-repository-uri` with
  an inline directory issuer — is a config error naming the signer and the
  issuer to add, never a silently inert entry. So is an inline issuer Sigmund
  cannot classify.

Matching is done against the list at verification time rather than by
expanding entries at load: the proven credential carries its issuer, so the
result already records which issuer vouched, and there is nothing to expand.

An entry without an issuer accepts the attribute from **any** listed issuer
that asserts it. `email: alice@example.org` with both keys.openpgp.org and
`https://github.com/login/oauth` listed is satisfied by either — which is the
backend independence identity-first verification wants, and also means the
entry is only as strong as the weakest listed issuer for that attribute. An
inline `issuer` replaces the list for that entry.

`subject` is one attribute, not the identifier. A GitHub Actions SAN —
`https://github.com/acme/widget/.github/workflows/release.yml@refs/tags/v1.2.3`
— carries the tag, so it changes with every release and cannot appear in a
policy that survives dependency upgrades. The stable attributes are the Fulcio
certificate extensions: `source-repository-uri`, `build-config-uri`,
`build-trigger`, `runner-environment`.

Choosing attributes trades stability against precision, and the docs state it:
`source-repository-uri` alone accepts any workflow in that repository,
including ones that are not the release pipeline, so pairing it with
`build-config-uri` — and, where it matters, `build-trigger` and
`runner-environment` — is the recommended shape.

### Directory identities: trusting future keys

An OpenPGP identity is proven in two steps. The signature proves the key; the
directory proves the address belongs to that key. So a UID becomes an
`IdentityCredential(https://keys.openpgp.org, {email})` only when **that directory
served it** for the signing key — never from the local GnuPG keyring, from
another keyserver, or from the evidence.

- **The directory is queried in its own right**, by fingerprint, whatever the
  `keyservers` argument says. Otherwise a command-line keyserver change would
  decide whether an identity resolves. Signatures usually name the signing
  subkey; keys.openpgp.org's `GET /vks/v1/by-fingerprint/<FPR>` accepts the
  fingerprint of a primary key or any subkey (upper-case hex, no `0x`), and the
  returned key is checked to hold that fingerprint. Lookups follow the
  `resolve-signers` switch that governs network key fetching: when it is off, a
  needed lookup leaves the claim `INDETERMINATE(KEY_UNAVAILABLE)`.
- **It is queried only when needed**: when no key credential of the signer
  already satisfies the clause. A signer carrying fingerprints and an email
  stays offline for the keys already pinned, and only a new key costs a lookup.
- **A binding proves the identity for signatures made before it was last
  observed.** The key store (P4.6) records each binding with the time it was
  first and last seen, refreshed under the key-freshness TTL. A refresh that
  still shows the address moves the last-seen time forward; one that no longer
  shows it stops it there. Rotation therefore does not erase history for a
  verifier that saw the binding, and nothing signed after the address left the
  key is covered — which also lets an owner withdraw an address. OpenPGP claim
  time is chosen by the signer, so this inherits the backdating risk stated in
  §1.1: someone holding a leaked, unrevoked old key can date a signature into
  the window.
- **Offline with no stored binding**, an identity requirement is
  `INDETERMINATE(KEY_UNAVAILABLE)`, never a pass.
- **Rotation unbinds history for first-time verifiers**, so a signer carries
  both: fingerprints for the keys already seen, which prove old signatures
  offline and forever, and the identity for keys to come. Bootstrap emits the
  fingerprints, and adds the identity — listing the directory — when the
  directory served a verified address for the key.

What this trusts, stated plainly: the directory's email verification and the
security of the email account. Whoever controls `alice@example.org` can verify a
new key for it. That is the price of accepting keys that do not exist yet, and
the same trade Sigstore email identities make.

### Config

```yaml
issuers:
  - keys.openpgp.org
  - https://token.actions.githubusercontent.com

signers:
  apache:
    pgp4: 4AEE18F83AFDEB23468B2E5A2D7BAF3C1E9F5A12   # keys already seen
    email: release@apache.org                          # keys to come
  release-bot:
    identities:
      - source-repository-uri: https://github.com/acme/widget
        build-config-uri: https://github.com/acme/widget/.github/workflows/release.yml
```

**A signer lists complete identities.** Each entry under `identities` is an
optional `issuer` and the attributes that issuer must have attested — the same
shape as `IdentityCredential` — so one form covers every issuer kind and a
signer may carry several, such as the same address from a directory and from
an OIDC provider:

```yaml
signers:
  alice:
    pgp4: 4AEE18F83AFDEB23468B2E5A2D7BAF3C1E9F5A12
    identities:
      - issuer: keys.openpgp.org
        email: alice@example.org
      - issuer: https://accounts.google.com
        email: alice@example.org
```

`email: <address>` remains as shorthand for an entry with only an address,
vouched for by the listed issuers. There is no backend-named block: a
`sigstore:` key would name how an identity is proven rather than who vouches for
it, and a directory address and an OIDC address would be written two ways.
Unknown signer keys are errors, so a misspelled or retired key fails at load
instead of silently dropping a credential. A signer has no display name; its id
is how rules and reports refer to it, and bootstrap writes the user ID a key
carries as a comment, since it proves nothing.

The trade-off against one typed block per issuer kind: the published JSON
Schema (ADR-007) can check attribute names against the union of all kinds'
vocabularies, so it catches a misspelling while it is typed, but it cannot tie a
name to the entry's issuer kind. That check — `source-repository-uri` from a
directory, say — happens at load, where the parser knows the kind.

### Key-material provenance

Every key records the source that supplied it — directory, keyserver URL, local
store, GnuPG keyring — and every claim carries it in its `TrustRootRef`.
Provenance is recorded always and consulted only for identities: a hostile
source cannot forge a fingerprint match, because the signature proves the key,
but it can serve any UID. `BcRunner.fetchKey` records the source of every key it
stores. It still prefers a keyserver copy that carries UIDs, so reports can show
who a key claims to belong to: with UIDs never matched, that preference affects
display text only and cannot widen acceptance.

### Consequence for §5.3

`keyservers` stays an argument: it fetches by fingerprint, a fingerprint is
proven by the signature regardless of who served the key, and UIDs from
keyservers never become identities. Issuers — listed or inline — are
policy-only, because they decide whether an identity is accepted at all, and
are covered by the policy digest.

### Consequence for the threat model

§1.1 claims defence against publisher account takeover producing releases under
a different key. That holds for `KeyCredential` policies. For
`IdentityCredential` policies the guarantee is inherited from the issuer:
whoever controls the OIDC account can obtain a certificate for the identity,
and whoever controls the email account can verify a new key at the directory.
Sigstore keyless has this property by construction, and §1.1 states that the
guarantee depends on the credential kind in use.

## Deferred

Recorded so the analysis is not lost, not scheduled:

- **Issuer profiles and a shipped base configuration.** Per-issuer settings —
  endpoint, trust root, what it asserts — declared in a file rather than known
  from the name. Needed once issuers exist that Sigmund cannot classify by name.
- **Configured directories.** Directories other than keys.openpgp.org, with
  their endpoints.
- **Several inline issuers on one entry.** One inline issuer or the default
  list covers the cases seen so far.
- **Attribute wildcards** — `*@example.org`, or a ref pattern on a SAN subject.
- **WKD and curated local key stores** as issuer kinds.

## Consequences

**Removed:** `EmailCredential`, and UID text as a matching input unless served
by a named directory.

**Renamed and reshaped:** `FingerprintCredential` → `KeyCredential`;
`SigstoreCredential` → `IdentityCredential` with an attribute map; `Credential`
becomes a sealed interface over the two.

**Config:** a top-level `issuers` list, empty by default, as the default for
identity entries; `identities` on a signer, each entry an optional `issuer`,
trusted for that entry only, and its attributes; `email:` as shorthand.

**Behaviour users would notice:** a `pgp4:` or `pgp6:` value shorter than a
full fingerprint is a config error; an `email:` entry is a config error until an
issuer that asserts email is listed; the `sigstore:` block and `name:` are
replaced by `identities` and rejected as unknown keys; an identity entry without
`issuer` accepts only listed issuers, where a `sigstore:` entry without one used
to accept any; a key in the local GnuPG keyring carrying a matching
address no longer satisfies anything; a publisher's new key is accepted without
a policy change once they verify it at the directory; `sigmund inspect-signer`
reports the source that supplied each key.

**Ordering:** implemented in roadmap phase P2, with binding storage and
freshness landing in P4.6. ADR-007 defines requirements, policy schema and
enforcement on top of these credentials.
